## A6-01 — cloning was a write to the source

`sandbox_clone.clone_catalog` constructed `Catalog` on the source to obtain ownership. That constructor sets WAL mode, creates/migrates tables, backfills metadata and commits. In the reproduction, cloning a DELETE-mode catalog without `meta` changed it to WAL and recreated `meta`; even a later missing-media refusal left the source changed.

**Implemented:** acquire the existing `writer(source)` lease directly, open SQLite with `mode=ro`, use the bounded online backup helper, and enumerate media rows from the completed destination snapshot. Never construct `Catalog` on the source. Schema upgrades may run on the disposable clone when its panel opens it. The normal diagnostic ownership lock may change; the promise concerns source database, application JSON and media, not the absence of lock bookkeeping.

**Closure evidence:** source schema, logical rows, journal mode and main-database bytes are unchanged after successful and refused cloning; the destination can still be opened/upgraded by the real `Catalog`. Existing committed-WAL, busy-writer and pending-migration regressions remain mandatory.

## A6-02 — a clone could contain the wrong media

Relative paths were resolved by searching the source before the project root. A source-local decoy shadowed the actual project-relative file. Only byte counts were compared after copying, so a same-length corrupted or concurrently changed copy was accepted. Replacing colons with underscores also aliases distinct legacy keys.

**Implemented:** resolve relative catalog paths against the documented project root; retain absolute archive paths. Read the snapshot's rows, copy independent bytes, and compare SHA-256 before copying, on the output, and again on the source. A mismatch fails the whole clone and removes only its owned output. Encode key UTF-8 bytes as hexadecimal for injective portable filenames; no content identity in SQLite is changed.

**Closure evidence:** shadow-path fixture copies the intended project file; same-length copy corruption and source mutation refuse; distinct legacy keys retain distinct files; existing external-archive and independent-storage tests pass. This remains cooperative copying, not protection from a hostile same-user process deliberately modifying files after verification.

## A6-03 — lifetime ownership started too late and ended too early

The wrapper cloned and published the ownership marker before acquiring its lifetime lock. A second sweeper could delete the completed catalog in that gap. Cleanup also ran after the lease ended, while deleting an in-directory lock undermines its stable-inode contract. The sweeper checked the marker only before acquiring ownership.

**Implemented:** `sandbox_session` owns construction, marker publication, serving and cleanup in one context. Its lease lives outside the removable clone, in `.panel-sandbox-leases`; tiny lock tombstones remain. Standalone `clone_catalog` owns construction and releases on return; serving callers must use the session API. Sweep rechecks the directory-bound marker under the same external lease before removal.

**Mixed-version safety:** marker protocol is v2. Old reclaimers recognize only v1 and cannot delete a new session; the new reclaimer leaves v1 directories alone because their old processes may still be alive. Do not automatically upgrade old markers or delete old directories based only on age/PID. Legacy leftovers are deliberately preserved, not silently called reclaimed.

**Closure evidence:** sweep injected immediately after marker publication cannot remove a constructing clone; actual subprocess ownership survives another sweep; process death makes reclamation possible; real wrapper → HTTP Save changes only the clone; failure cleanup restores the caller environment; the external lock inode survives directory removal. No test uses the owner's real temp root or catalog.

## A6-04 — atomic JSON writers shared another file's temporary inode

`write_json_atomic` opened the fixed `<destination>.tmp` in truncating mode. A pre-existing unrelated file was overwritten and renamed away. Two simultaneous writes shared it; after one replace the other failed with `FileNotFoundError`. Serialization, fsync and replace failures left partial temporary output behind.

**Implemented:** exclusive `tempfile.mkstemp` creates a unique sibling for each invocation. Preserve JSON encoding, file flush/fsync and atomic replacement; close the handle and remove only this invocation's temporary path on every exit. A unique temp file does not replace the caller's domain lock around read-modify-write operations or make SQLite plus JSON one transaction. This change does not claim full power-loss durability on every filesystem.

**Closure evidence:** unrelated `.tmp` sentinel survives success and all three injected failure points; failed writes retain the original destination; two writers synchronized at replacement both finish with complete JSON and independent temps; no owned temporary residue remains.
